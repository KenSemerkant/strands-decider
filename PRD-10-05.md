# PRD — Cross-request state cache and benchmark suite for MLX serving

Status: draft (not yet published to the tracker). Triage label when published:
`ready-for-agent`.

## Problem Statement

An operator serving the decider on Apple silicon pays the full state-encoding forward on
every request, even when consecutive requests are about the same text. Interactive
agent workflows — the Strands tool-call intervention pattern in particular — ask
follow-up questions about one conversation state in separate HTTP requests. Each of
those re-reads the whole state from scratch: the same ~1400-token state sent 40 times
cost about 98 ms per request, every time, when the encoded state could have been reused.

Separately, nobody could answer "how fast is this, on what workload, and did a change
regress anything?" without hand-rolled commands. The repository's engine-level latency
sweeps exist, but nothing measured the served system end to end, nothing measured it on
real corpora with gold labels, and nothing exercised the repeated-state pattern that
agents actually produce.

## Solution

The MLX engine keeps a bounded, LRU cache of encoded states across requests, keyed on
the state's post-truncation token ids. A request that arrives with a state the engine
has already encoded forwards only its question suffixes against a copy of the cached
encoding — repeated states drop from ~98 ms to ~19 ms on long states. The cache is
populated as a side effect of the multi-question path that already encodes the state
alone, so no request ever pays an extra forward to warm it, and a cache miss behaves
exactly as before. Capacity is operator-controlled (`--state-cache N`, default 8, 0
disables) and reported through the health endpoint.

Alongside it, a benchmark suite that measures the served system: a synthetic sweep
(state length, questions per request, choice width, mixed types, cache hit/miss,
concurrency, full-window steady state), a 1000-per-type type benchmark, a real-corpus
benchmark that replays labelled training records through the server and reports
latency, accuracy and confidence-when-right-vs-wrong, and a frozen-torso comparison
harness that reads Qwen3.5-4B through its chat template with option-letter logits.
One command runs all of them against a live server.

## User Stories

1. As a serving operator, I want repeated states to skip re-encoding, so that
   interactive agent traffic on one conversation is answered in ~19 ms instead of ~98 ms.
2. As a serving operator, I want the cache capacity exposed as a CLI flag, so that I can
   size it to my workload's distinct-state working set.
3. As a serving operator, I want `0` to disable the cache entirely, so that I can A/B
   latency or rule the cache out when diagnosing.
4. As a serving operator, I want the health endpoint to report the cache setting, so
   that I can verify what a running server actually has.
5. As a serving operator, I want a cache miss to cost exactly what it did before this
   feature, so that one-shot workloads see no regression.
6. As a serving operator, I want cached and uncached answers to be identical within
   float tolerance, so that enabling the cache never changes a decision.
7. As a serving operator, I want the cache to evict least-recently-used entries under
   pressure, so that memory stays bounded no matter how many distinct states arrive.
8. As a serving operator, I want snapshots isolated from the fan-out that reads them,
   so that a later request against the same state is not corrupted by an earlier one.
9. As an SDK developer, I want the cache configurable on the engine loader, so that
   library embeddings get the same control as the CLI.
10. As an SDK developer, I want a public counter of state encodes, so that I can assert
    cache behaviour in my own tests and dashboards.
11. As an agent developer, I want a state encoded once to serve any later question —
    any type, any option count, any wording — so that my follow-up questions are nearly
    free without my code knowing the cache exists.
12. As an agent developer, I want a request with many questions about a cached state to
    still amortise the state, so that batch interrogations stay cheap.
13. As an agent developer, I want the intervention pattern (multi-question first, then
    single-question follow-ups) to hit the cache, so that the documented Strands
    example workflow gets the full speedup.
14. As a benchmarking engineer, I want a one-command benchmark runner, so that I can
    measure the whole served system without assembling commands.
15. As a benchmarking engineer, I want a synthetic sweep over state length and question
    count, so that I can characterise scaling independently of data.
16. As a benchmarking engineer, I want choice width swept to 50 options, so that I know
    the pointer head's cost curve.
17. As a benchmarking engineer, I want cache hit and miss measured separately, so that
    the cache's contribution is visible and regressible.
18. As a benchmarking engineer, I want concurrency measured at several client counts,
    so that throughput ceilings are documented, not guessed.
19. As a benchmarking engineer, I want a 1000-tests-per-type benchmark, so that warm
    steady-state latency per question type is established with tight percentiles.
20. As a benchmarking engineer, I want the benchmark to replay real labelled corpora,
    so that latency is measured on a realistic token distribution and accuracy is
    reported alongside as a correctness tripwire.
21. As a benchmarking engineer, I want instruction-paraphrase consistency measured, so
    that question-sensitivity regressions surface in perf runs.
22. As a benchmarking engineer, I want a frozen-4B comparison harness, so that model
    decisions are argued against a measured baseline rather than published numbers
    alone.
23. As a CI maintainer, I want the corpus-record-to-API mapping covered by unit tests,
    so that a schema drift in the corpora or the API fails loudly instead of silently
    producing a benchmark that measures the wrong thing.
24. As a CI maintainer, I want engine cache behaviour covered by the existing tiny-
    checkpoint MLX harness, so that correctness pins run on every machine that can run
    the existing suite, with no network and no model download.
25. As a maintainer, I want the mlx-lm re-merge limitation documented at the
    workaround, so that the next engine change does not rediscover it.

## Implementation Decisions

- The cache lives in the MLX engine, not the server: every consumer of the engine
  (HTTP, CLI ask, library) gets it, and it sits under the engine's existing
  single-evaluation lock, which already serialises request state.
- Keying is on the state's post-truncation token ids — the exact ids that were encoded
  — so two requests with equal text but different question sets share an entry and
  truncation cannot alias two different states.
- Population happens only on the shared-prefix path (requests with ≥2 questions,
  including each chunk of a chunked request), because that path already builds a
  state-only encoding. Single-question requests only read. This mirrors the engine's
  existing gate that keeps one-question requests on the cheaper whole-prompt path.
- A snapshot is a batch-1 copy of every prompt-cache layer; serving a hit fans the
  snapshot out to the request's question count with the cache implementation's own
  merge, which copies rather than mutates. Hybrid-torso state (Gated DeltaNet
  recurrent and conv states) is copied by the same mechanism.
- Workaround (from the prototype): merging a merged KV cache a second time raises,
  because the merged form carries a per-row array offset that cannot slice. Snapshots
  of KV layers are therefore converted back to the plain integer-offset cache form;
  recurrent-state layers already round-trip and pass through. This is documented at
  the conversion helper.
- Token accounting on a hit reports the full prompt size (state + questions), matching
  the shared-prefix path's semantics: usage describes the prompt, not the compute
  reused.
- Capacity is a single integer, LRU eviction, default 8, zero disables; exposed on the
  serve CLI, the app factory, the engine loader, and the health endpoint. The default
  is deliberately small: an entry's memory scales with state length, and an
  undersized cache silently yields zero benefit (measured: 60 states through 8 entries
  gained nothing; through 128 entries, 2.3×) — the health field exists so operators
  can check it against their working set.
- The benchmark suite is three HTTP-driving scripts plus a frozen-model comparison
  script and a shell runner; none are imported by production code. The corpus
  benchmark's record mapping is a set of pure functions so tests can pin it without a
  server.
- The frozen-4B comparison reads the torso through its chat template with one forward
  pass per task and a softmax over option-letter logits, excluding nothing; score
  tasks are reported separately because letter logits cannot express ordinal expected
  value. The thinking-model read position (after an empty think block, not at the
  generation prompt) is documented in the script — reading at the prompt scores 0.355,
  at the answer position 0.710.

## Testing Decisions

Good tests here pin external behaviour: the same request must produce the same answers
with the cache on, off, cold, and warm; the observable knobs (counter, health field,
flag) must reflect reality. Nothing asserts internals like snapshot structure.

- Primary seam (existing, preferred): engine `evaluate` through the tiny random
  checkpoint harness the MLX engine tests already use — pointer and slot heads, Apple
  silicon only, no downloads. Cache correctness pins: a repeated state is encoded once
  (counter), a single-question request reuses a populated entry and matches uncached
  answers within 1e-4, LRU eviction order under capacity 1, and capacity 0 disabling
  the cache. The harness's existing repeat-request and chunking parity tests now also
  exercise warm cache hits implicitly.
- Secondary seam (existing): the HTTP app through its in-process test client — flag
  plumbing and the health field.
- Bench mapping seam (new, narrow): the corpus-record → API-question mapping and the
  answer-checking functions as pure functions; prior art is the schema-round-trip
  style already used in the suite. No server, no network.
- End-to-end validation performed once, out of band: the full public JevBench set
  through the cached server (0.766, Brier 0.3231 vs published 0.762 / 0.323) —
  recorded as evidence, not as a CI gate, matching how the repo treats single runs
  with known noise.

## Out of Scope

- Any equivalent cache on the torch (CUDA/MPS/CPU) engines. The torch path's
  intra-request prefix cache already exists; a cross-request cache there is a separate
  design with different memory tradeoffs.
- Batching concurrent requests that share a state into one forward (the cache serves
  them sequentially; GPU serialisation makes the win small today).
- Any change to model weights, training, or the published checkpoints.
- Making the benchmarks part of CI. They need a live server and a warmed model; they
  are operator tools, with only their pure mapping functions under test.
- Vision (`--vision`) serving; it runs on torch devices only and is unaffected.

## Further Notes

- Measured headline numbers (M5 Max, MLX, warm): repeated ~1400-token single-question
  state 98.2 → 18.8 ms (5.2×); real-corpus grouped states 52.3 → 22.4 ms (2.3×); hit
  latency is type-blind (17.7–18.6 ms across noul, choice 2–10 options, score).
- Three gpu-variant parity tests in the existing MLX suite drift by 0.0003 against the
  1.5e-4 tolerance on unmodified code on this hardware (Metal kernel numerics). They
  predate this work; the tolerance question is a separate maintenance decision.
- The frozen-4B comparison's per-family result names the next training lever:
  probability, tradeoff and multi_hop are learnable (the 4B has them; the 2B decider
  does not), and the released recipe's teacher-distillation step extends to generated
  data for exactly those families.
